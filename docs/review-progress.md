# 確認状況・差分 — 外部エージェント用の永続チェックポイント

## 使い方

サイドバーの「確認状況・差分」で、クラス・型とメソッドを状態別に表示します。外部エージェントは `tenka_context` の後に `tenka_review_queue` を使い、未確認・要再確認だけを取り出して調査を続けられます。閲覧だけではチェックを付けません。Webは表示のみで、モデル接続・記録の変更・コード実行を開始しません。

状態は次の4種類です。

| 表示 | 意味 |
|---|---|
| 未確認 | 記録なし、または理由付きで明示的に未確認へ戻した状態 |
| チェック済み | エージェントがその版を調べ終えた作業記録 |
| 最適化済み | エージェントが最適化作業を終えたと記録した状態。速度改善の証明とは別 |
| 要再確認 | 記録後に対象のソース、同じプロジェクト・参照先の読み込み済みソース、明示的なプロジェクト設定等が変更された状態 |

要再確認には「対象本体のソース変更」「周辺コード変更」「読み込み後のファイル変更」の理由と、以前の状態を残します。クラスのチェックを付けても、各メソッドは勝手にチェック済みになりません。最適化済みでも未測定であればsummaryにその旨を記録してください。ツールが返した成功/失敗とエージェントの主張は混同しません。

## 外部エージェントの標準手順

1. `tenka_context` → `tenka_review_queue(snapshotId, state="pending", kind="method")` で未確認・変更済みを取得。
2. `target.selectionId` を既存の `tenka_inspect_method` / `tenka_inspect_type` に渡して調査。通常のIDはスナップショットごとに変わります。
3. `tenka_review_target(snapshotId, targetId)` で現在のsourceHash・contextHash・state.revisionを確認。
4. 調査後、`tenka_mark_review` で `checked` を記録。summaryに確認範囲と未確認事項、必要なら同じセッションで完了したevidenceCallIdsを含めます。
5. 外部エージェント自身の編集ツール等で修正した場合、甜花ちゃんではプロジェクトを再読み込みします。甜花ちゃんのこの機能はソースを書き換えません。
6. `tenka_review_queue` / `tenka_review_target` を再取得し、変更前の確認記録と `tenka_review_diff` で比較。必要なテスト・ベンチマークを実行して結果を確認します。
7. 改善作業を終えた場合だけ `optimized` を記録。未測定・一部未検証という制限もsummaryに書きます。

例（値は直前のツール応答から取得。固定値を使い回さないでください）：

```json
{
  "snapshotId": "CURRENT_SNAPSHOT",
  "targetId": "target.id",
  "sourceHash": "target.sourceHash",
  "contextHash": "target.contextHash",
  "expectedRevision": 0,
  "status": "checked",
  "summary": "所持品検索の列挙と割り当て候補を確認。性能計測はまだ実施していない。",
  "evidenceCallIds": ["COMPLETED_INSPECTION_CALL_ID"]
}
```

expectedRevisionは初回のみ0、以後は最新のstate.revisionです。他のエージェントが先に更新した場合は競合エラーとなり、履歴を上書きしません。古いソース/周辺コードのハッシュや、ディスク上のコードが読み込み時点と違う状態での記録は拒否します。承認済みの対象アプリを実行する許可とは別で、マーク自体は実行を伴いません。

## 追加した5つのMCPツール（合計36ツール）

- `tenka_review_queue`：stateとkind、プロジェクト、名前で絞り込み、ページ単位で取得。pendingが既定。
- `tenka_review_target`：現在の状態・ソース/周辺ハッシュ・最新リビジョン・履歴。
- `tenka_mark_review`：checked / optimized / unreviewedを理由・参考証拠付きで記録。
- `tenka_review_diff`：確認時点と読み込み済みソース、または保存した2つのリビジョンの行差分。
- `tenka_review_history`：サーバー再起動後も残るチェック履歴をページ単位で取得。

## 差分の表示

「確認状況・差分」で対象を選び、比較元と比較先を選択します。追加行・削除行を色と+/−で区別し、前後の行番号を表示します。行番号は保存した対象ソース内の番号で、元ファイルの絶対行番号ではありません。partial型はファイル名の見出しを付けてまとめます。

既定の比較は最後の記録と読み込み済みソースです。最適化済みを記録した直後は差分ゼロになります。最適化前後を見るときは、比較元に以前の「チェック済み」の記録、比較先に「最適化済み」の記録を選びます。比較元がない対象はソース全体を表示しますが、それを変更量とは呼びません。

これは記録したソース同士の差分で、Gitコミット/インデックス/ワーキングツリー全体のdiffではありません。未コミットの変更でも、再読み込みしたソースと確認記録の比較はできます。大きい変更は区間全体の置換へフォールバックし、最小差分でないことを表示します。行はページングし、ファイルを書き換えたりgitコマンドを実行したりしません。

## 永続化・整合性・範囲

`TENKA_DATA_DIR` 配下（未指定時はローカルアプリデータの `tenka-chan`）の `review-progress.sqlite` に保存します。ブラウザーやサーバー、外部エージェントを再起動しても、同じ配置のプロジェクト・宣言シグネチャ・ソースであれば記録を復元します。古い本文も差分用に保存するため、このDBにはソースコードが含まれます。機密情報として扱い、共有/Git登録しないでください。

永続IDはプロジェクトの正規化された絶対パスと宣言シグネチャから作り、RoslynのセッションIDや行番号に依存させていません。オーバーロード、別のプロジェクト、型とメソッドを区別します。改名・署名変更・別チェックアウトへの移動は別対象とし、自動的な引き継ぎはしません。削除済み宣言や過去の別名を探索する専用UIは未追加ですが、既存の履歴は削除しません。

同じプロジェクトやその参照先のソース変更は保守的に要再確認にします。厳密な呼び出し依存解析ではないので、本体に差分がなくても周辺変更として表示される場合があります。ファイル追加を含む編集後はプロジェクトを再読み込みしてください。検査対象は読み込み済みのC#文書・明示的.csproj・選択したコンパイル/パース設定です。任意のMSBuildインポート、まだ読み込んでいない新規ファイル、外部バイナリ、ランタイムや実行環境までの完全同一性は保証しません。

記録時には読み込み済み文書の内容をディスクから再ハッシュします。表示用チェックは3秒間キャッシュし、画面は5秒ごとに表示を更新します。チェック直後に別プロセスが変更する競合自体は排除できませんが、保存記録は常に特定のソースハッシュに結び付き、次の再確認で変更を検出します。チェック済みは安全性の証明ではありません。

上限は索引2万対象、入力/保持ソース各6400万文字、対象ごとの保存本文20万文字、diff2万行です。保存DBは2万リビジョンまたは本文総量6400万文字で新規書込みを停止し、古い履歴を勝手に破棄しません。匿名関数・局所関数や完全な本文を取得できない対象は個別マーク不可として理由を表示します。

証拠には完了した同一セッションの呼出しID、ツール名、返却状態などを複写します。セッションが終了してもこのメタデータは残りますが、測定結果の全本文をチェックDBにコピーする機能ではありません。テスト失敗もそのまま保存し、別対象の実験結果やLLMの自己申告を性能改善の証明に昇格させません。
