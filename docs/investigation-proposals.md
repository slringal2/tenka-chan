# 調査を引き継ぎ、元コードを壊さず候補を比較する

2026-10-16。PR #20の `e6a0bdf` に続く変更です。
目的は検出ルールを増やすことではなく、調査AIが接続・ID・実験の配線を繰り返す手間を減らすことです。
本体は.NET 10、対象側のフレームワーク方針は変更しません。新しいパッケージ、Docker要件、CIは追加しません。

## 調査担当としての評価から変えた点

低水準ツールを全部順番に呼ぶこと自体には価値がありません。単純なコードなら直接読む方が合理的です。
価値を出すべき箇所を「同じ条件で検証する」「中断しても根拠を引き継ぐ」「他の編集を壊さず適用する」に絞りました。

- 通信セッションを終了しても、調査IDに紐づく実験所有権と完了呼び出しの根拠を残す。
- 高水準の入口から変更対象のファイル全文・正確なファイルハッシュ・既存検証候補を返す。
- 変更前／変更後の独立コピーに同じテストとベンチを適用し、結果と途中経過を保存する。
- 性能の測定と元コードへの適用、確認済みの記録を別の操作にする。

これで通常のエージェントより早く調査できたとはまだ主張しません。実機での比較は未実施です。

## 永続的なinvestigationId

新しい各通信セッションは独立した調査IDを持ちます。`tenka_context.investigation` または次で確認します。

```text
tenka_investigation {"action":"status"}
tenka_investigation {"action":"list"}
tenka_investigation {"action":"resume","investigationId":"取得済みID","approved":true}
```

`resume` は既存のローカル資格情報を持つクライアントに、選んだ調査の結果・実験・候補への利用権を与える明示的操作です。
同名のclientNameだから同じ本人と推定する仕組みではありません。多利用者を隔離する認証機能でもありません。
別の操作がその調査を使用中なら復旧操作も待ち行列に入れず拒否します。実行中の処理は停止しません。

`TENKA_DATA_DIR` の下の `investigations/<id>` に、完了呼び出しのメタデータと小さな応答、実験ID、候補IDを保存します。
根拠は元のinstanceId、callId、ツール、失敗／キャンセルを含むoutcomeを維持します。
`tenka_mark_review` と `tenka_note` は、この調査に属する完了呼び出しを参照できます。
実験の既存のファイル検査・実行許可・一度限りの実行条件は維持します。

`tenka_read_result` は現在セッションに大きな結果があればそれを優先し、なければ保存した小さな応答へ進みます。
大きなライブ専用結果はメタデータだけで、後から全文を作り直したり解析を再実行したりしません。
変更前の版で作られたセッション所有権・根拠は、保存されていないため遡って復元できません。
各調査の上限は呼び出し512、実験256、候補128です。古い根拠を黙って消して空きを作ることはしません。
ディレクトリの一覧は200件までで、上限に達した場合はlimitedを返します。

保存失敗は、実行が始まっていない／失敗したという意味ではありません。
応答の `persistenceWarning` を確認し、保存のためだけに対象処理を再実行しないでください。
同じrequestIdの完了済み結果は従来どおり実行前にキャッシュを返します。
保存フォルダーにはソースやログが含まれます。接続資格情報だけでなく、これらも共有・Git登録前に確認してください。

## 既存ファイル1つの変更候補

```text
tenka_review_workflow {"targetId":"現在の対象ID"}
```

最初の呼び出しは参照のみです。返された `editInput.source` を読み、同じ対象について次を送ります。

```text
tenka_propose_change {
  "targetId":"対象ID",
  "snapshotId":"返されたスナップショット",
  "expectedFileSha256":"editInputの値",
  "replacementCode":"変更後のファイル全文"
}
tenka_diff_proposal {"proposalId":"作成結果のID"}
```

対象を読み込み済み索引から解決し、読み込み後の変更を再検査します。任意のファイルパスを渡すAPIではありません。
既存ファイル1つ、変更後6万文字までです。UTF-8・UTF-16のBOMと元の改行形式を引き継ぎ、元のバイト列を別に保存します。
UTF-32など対応外の形式は書き換えません。C#の構文エラーがある置換は拒否しますが、コンパイル成功は別の検証です。

ソリューション／既知のプロジェクトが収まる範囲を、独立したbaseline/candidateフォルダーへコピーします。
ファイルを共有するハードリンクは作りません。既定の上限は8,000ファイル、16,000エントリ、合計128 MBです。
`.git`、`bin`、`obj`、`.vs`、`.idea`、`node_modules`、`.tenka` などはコピー対象外です。
完全な秘密情報検出機能ではなく、設定ファイルやソース内の秘密がコピーに含まれることはあります。
ファイルの追加・削除・内容変更を含め、検証の前後で取り込んだ入力を再検査します。

コピー外のProjectReference/Import/HintPath、動的／絶対の入力パス、出力ディレクトリの独自指定、範囲外の親Directory.Build.props等は未対応として止めます。
複雑なOSSやリンクしたソースで止まる場合があります。元プロジェクトを無断で書き換えて合わせることはしません。
この範囲確認はセキュリティサンドボックスではありません。SDKや任意のビルド処理の副作用まで閉じ込める機能ではありません。

## 同条件の検証と途中からの続行

```text
tenka_review_workflow {"proposalId":"候補ID","mode":"validate","approved":true}
```

既存テストとBenchmarkDotNetの候補がそれぞれ唯一なら、その組を使います。複数候補なら、候補作成時に返された
`testCompanionId` と `benchmarkCompanionId` を最初の検証呼び出しで指定します。
`benchmarkFilter` は任意で、既定は `*`。指定すると同じフィルターを両方のコピーで使います。
選択とフィルターは最初の検証開始で固定します。既存テスト・ベンチのないプロジェクト向けに、期待値や測定コードを自動で捏造するものではありません。
既存の生成実験は引き続き別に作成・実行できますが、生成実験をこの候補パイプラインへ直接組み込む機能は残作業です。

段階は、変更前テスト → 変更後テスト → 変更前ベンチ → 変更後ベンチです。
テストが失敗・空・スキップを含む場合は後続へ進みません。終了コード0だけで成功とは扱いません。
ベンチは同じケース・環境指紋、正の有限な平均、観測数を確認します。
ケース欠落や環境不一致、5観測未満を有効な比較と扱いません。CLIでは同じ短いジョブ・5回の観測・3回のウォームアップを依頼します。
これは要約統計の比較であり、統計的有意差や本番性能の証明ではありません。
複数ジョブが同じケース名を返した場合も、勝手に混ぜず比較不可とします。

呼び出しはフォアグラウンドで動きます。長くなる場合は完了した段階を保存して `awaiting_next_stage` を返します。
同じproposalIdと `mode:"validate"` で、明示的に承認して続きを呼びます。
完了済み段階を再実行しません。処理中断・サーバー終了などで開始記録だけが残った段階は結果不明として拒否し、勝手な再試行はしません。
失敗段階の強制的なやり直し・既存成果物の破棄は実装していません。必要に応じて原因を直して新しい候補を準備します。

```text
tenka_review_workflow {"proposalId":"候補ID","mode":"result"}
```

結果は候補とともに永続化されます。調査をresumeすれば、新しい通信セッションからも結果を読めます。
テストが変更対象を十分にカバーしているかは別問題です。参照関係やフィクスチャの意図、測定対象を調査AIが確認してください。

## 適用・取り消し

```text
tenka_apply_change {"proposalId":"候補ID","approved":true}
tenka_revert_change {"proposalId":"適用した候補ID","approved":true}
```

適用は、実際に選ばれた両テストの全件合格と、両ベンチの有効な比較を保存した候補に限ります。
「validation_completed」という文字列だけでは足りず、4段階の内容も再検査します。
比較が完了していても高速化したとは限りません。遅くなった結果を含め、結果を読んで適用の是非を判断してください。
元の入力とファイルの現在バイト列が取り込み時と違えば、強制上書きせず停止します。
取り消しは、適用後のバイト列から変わっていない対象にだけ、元のバイト列を戻します。

同じディレクトリの一時ファイルから置換し、実際に退避されたファイルをバックアップとして残します。
別エディターが同時に名前変更するケースを、移植可能なAPIだけで完全なcompare-and-swapにはできていません。
競合を検出した場合や完了記録を残せず中断した場合は、バックアップを消さず手動確認に止めます。
`tenka_diff_proposal` で状態・liveFileHash・backupPathを確認できます。自動復旧や盲目的な再適用はしません。
**複数ファイルの原子的適用、Git全体のrevert、サンドボックス実行は未実装です。**

元ファイル変更後の再読み込み、確認記録、意味的な正しさの判断は自動では行いません。
