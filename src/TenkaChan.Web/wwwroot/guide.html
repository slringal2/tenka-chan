① まず、持ち物検索を解析する

上の「サンプルの準備へ」でパスを入力済みの準備画面を開きます。「読み込む」→ 初回は「NuGet依存関係の復元」を許可 →「Releaseビルドして準備する」の順に進みます。「成功後に解析」はオンのままにします。サンプル本体に外部パッケージはありませんが、SDKの参照パック等の準備は必要です。

② 実際に動かして、GC・割り当てを観察する

ビルド後、「プロファイル取得」で次の設定を入力します。詳細ランタイムイベントをオンにし、信頼済みの実行を承認します。ベースラインと改善版の採取は別々に行ってください。各採取のcapture.jsonを残し、「保存イベントを解析」へ進みます。

実行DLL（ビルド後に作成）bin/Release/net8.0/Tenka.Sample.GameLab.dll
保存先（付属の既存フォルダー）samples/Tenka.Sample.GameLab/profiles
ベースラインのアプリ引数（JSON配列）["--scenario","inventory","--mode","baseline","--seconds","4"]
改善版のアプリ引数["--scenario","inventory","--mode","optimized","--seconds","4"]

取得制限は60秒を目安にしてください。4秒間の処理回数は版ごとに異なるため、総割り当て量をそのまま「1回あたりの改善率」とは比較しません。GCが観測されない場合もあります。正確な1回あたり比較は③を使います。スレッドのサンプル時間をCPU使用率そのものと解釈しないでください。

ロック競合も試す

シナリオをcontentionに変更します。4ワーカーで長いlockを繰り返す版と、独立した仕事をlockの外へ出してまとめて加算する版があります。どちらもカウンターの結果は一致する設計です。観測できる競合量はOS・スケジューリングで変わります。

["--scenario","contention","--mode","baseline","--size","300","--seconds","4"]

プロファイル取得へ

機械語は「なぜ差が出る？」を調べる道具

「性能ホットスポット」でサンプルDLLを選び、JIT対象に下のどちらかを指定します。サンプルは引数なしで両メソッドを呼ぶので、最初から特別な呼び出しコードを書く必要はありません。

剰余演算の版DamageBuckets:SumModuloビット演算の版DamageBuckets:SumMask

入力を「非負の整数」「バケット数は2のべき乗」に限定して、同じ結果になる2つの実装です。一般の符号付き剰余を無条件に置き換える例ではありません。JITがどの命令に変換するかを比較します。命令数が少ないだけで高速と判定しません。

教材では対象メソッドが一覧から消えないようNoInliningを指定しています。最適化自体は無効にしていません。実プロジェクトでは同じ属性が必要とは限りません。

JITを取得する保存したIL・機械語を見る

③ 同じ結果になることと、速さを分けて確認する

サンプルフォルダーのrun-lab.batを開きます。1は参考計測、2は外部パッケージ不要の35比較、3はxUnit、4はBenchmarkDotNetです。どれも選んだときだけ実行します。最初は2、その後4がおすすめです。通常のベンチマークには数分かかります。

サンプルフォルダーsamples/Tenka.Sample.GameLab

xUnitでは重複・空配列・負数・境界値・無効な引数なども確認します。BenchmarkDotNetでは同じ入力を使い、HashSetや文字列の構築コストも測定に含めます。「数倍速くなる」といった固定値は教材に埋め込みません。

甜花ちゃんの「テストと性能」で、生成実験も試す

解析対象をGameLabのままにして、xUnitを選び、次のコードを「C#コード」に貼り付けます。「実験を準備する」後、内容を確認して「ホストで実行」を承認します。付属Testsプロジェクトの実行とは別の機能です。

using Xunit;
using Tenka.Sample.GameLab;
public class InventoryCheck {
    [Fact] public void ResultsMatch() {
        int[] owned = { 1, 2, 2, 4 };
        int[] requested = { 2, 3, 2 };
        Assert.Equal(2, InventorySearch.CountOwnedFast(owned, requested));
        Assert.Equal(InventorySearch.CountOwnedSlow(owned, requested),
                     InventorySearch.CountOwnedFast(owned, requested));
    }
}

BenchmarkDotNetを選んだ場合は次のコードを使えます。2メソッドの比較はこの1回のレポート内で確認します。別々の実験ID比較とは異なります。

using BenchmarkDotNet.Attributes;
using Tenka.Sample.GameLab;
[MemoryDiagnoser]
public class InventoryCheck {
    private int[] owned = null!, requested = null!;
    [GlobalSetup] public void Setup() {
        var data = GameData.Create(600);
        owned = data.Owned; requested = data.Requested;
    }
    [Benchmark(Baseline = true)] public int Before()
        => InventorySearch.CountOwnedSlow(owned, requested);
    [Benchmark] public int After()
        => InventorySearch.CountOwnedFast(owned, requested);
}
テストと性能へ

生成テストは現在のユーザー権限で動きます。未確認のコードを実行しないでください。AI自律レビューは任意の次の段階で、ここまでの教材にはモデルの起動は不要です。

何が終わればよい？

「問題のあるソースを見つけた」「改善版と結果が一致した」「時間と割り当て量を実測した」の3点を説明できれば、最初の一巡は完了です。プロファイルやJITは原因を詳しく追うときに足してください。

サンプルや画面を開いただけでは、解析・テスト・計測は開始しません。サーバーを再起動した場合はプロジェクトを再度読み込みます。
